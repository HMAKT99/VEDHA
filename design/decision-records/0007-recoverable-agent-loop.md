# ADR-0007: The agent loop recovers from mistakes, but never repeats a possible side effect

Status: accepted.
**Context:** LLM pilot 1 (`benchmarks/llm/README.md`): a model completed healthy tasks on plain Playwright and none through Vedha. In every Vedha trial the order request was never sent: the model tried `fill` on a dropdown, got a raw Playwright error, and `explore()` ended the run at the first failed step. Three product weaknesses: no recovery from agent mistakes, errors an agent cannot act on, and an observation without page text.
**Decision:**

1. `explore()` shows a failed step to the actor and continues (`onStepFailure: "feed_back"`, default), bounded by `maxSteps` and `maxConsecutiveFailures` (3). Every failed step stays in `session.results`, the report verdict and the failure bundle; the promoted test excludes it.
2. It never lets the actor repeat a step that may have had an effect, but it does not end the run. A `RepeatGuard` (core, shared with the MCP server) refuses to run a mutating action again while an earlier attempt of the same action (same op/target/value, or the same stated intent) is unresolved: `outcome_unknown`, or failed with an error class that could have followed dispatch. The refusal is recorded as a blocked step with `error.code = "repeat_refused"`, shown to the actor, and excluded from the run verdict. An unresolved effect is cleared by an independent check: a later non-mutating step with at least one declared check and `confirms: "<earlier id>"`; the earlier result keeps `outcome_unknown` but gains `confirmedBy`, and the run verdict becomes `passed_with_recovery`.
   _Revision note:_ the first version stopped the whole run (`unsafe_to_continue`) after any such step. Pilot 2 (`benchmarks/llm/`) showed why that was too blunt: the model had declared a wrong check (`text_contains "Ada"` against an input value), the order was placed, Vedha correctly reported `outcome_unknown`, and the run ended before the model could look at the page and confirm. Pilot 2 itself ran on that first version (commit bbd7985).
3. `ErrorInfo.hint` gives advice derived from the error class, the target role and one bounded read of nearby controls. `invalid_action` is raised before anything is sent when the stated role cannot take the op (a pre-flight check limited to roles that clearly cannot; `combobox` is excluded because it covers editable inputs, so that case is classified after the attempt). Hints quote page names as data.
4. `renderFeedback` is the single text shown to any actor or tool server: outcome, failed checks, hint, recoveries, then the page (full outline while complete, controls list once the outline is truncated).
5. Page-health check (`Policy.health`, default `mutating`; also applied to `outcome_unknown` results): a step whose declared checks passed still fails with `health_check_failed` if, while its final attempt ran, any response was 5xx, a write returned 4xx or failed, or the page threw an uncaught exception. Endpoints the step verifies with a network check, or lists in `healthIgnore`, are exempt. It looks only at the final attempt's window, so an earlier failure preserved in a `RecoveryRecord` is not double counted.
   **Consequences:** + agent mistakes cost a step, not the run; + a UI that says success while the server says 500 is reported as failed without the author or model declaring a network check; − default behaviour of `explore()` changed (v0.1 unpublished); − a mutating action that hits a legitimate 4xx (for example validation) must be declared with a network check or `healthIgnore`; − hints add a few hundred characters per failure.
   **Evidence:** scripted gate, 75 trials: identical outcomes to the post-fix run; observation-size track medians unchanged; pilot 2 results in `benchmarks/llm/`.

## Addenda (2026-10-20)

- **Idle-aware classification:** when the action completed without error, a declared check is unmet, the adapter reports no request in flight and there is no reconcile probe, the step is `failed` with `error.code = "expectation_not_met"`, not `outcome_unknown`. A late effect needs a pending request; with none, the unmet check is a failure. It is still never repeated (RepeatGuard keys on the possible effect) and `confirms` can clear it if the check itself was wrong (health-check failures and definitive contradictions cannot be cleared). Adapters that cannot report in-flight requests keep `outcome_unknown`. Evidence: TodoMVC client-only mutants went from 12/20 correct (rest "uncertain") to 50/50 at n=5, with held-out and S01-S15 outcomes unchanged. Limitation: long-lived requests (SSE, long polling) keep the page "not idle", so those stay `outcome_unknown`.
- **Final report turn (from browser-use, E-095):** after the consecutive-failure limit, `explore()` gives the actor one last call that may only report (`final: true`); the report is returned as `finalReport`. The MCP server appends a warning after three failed steps in a row.
- **Page header and request lines (from Playwright MCP, E-091):** feedback includes the tab list when there is more than one tab, a non-2xx main-document status, console error/warning counts, the writes and failures a step made ("POST /api/orders 201"), and, for MCP results, what changed on the page since the previous observation.
- **Read-back inference (P1, `readback.ts`):** after a mutating step whose write requests returned 2xx, Vedha reads the data back through the same session (POST /x then GET /x lists the item; PUT/PATCH then GET shows the fields; DELETE /x/1 then GET /x no longer lists id 1) and fails the step with `readback_contradiction` if a JSON collection answers and clearly lacks the item. Silent when the convention does not hold: GET unsupported (404/405), non-JSON, a non-empty list whose items share no key with the write (different schema), or 100+ items (pagination risk). Created ids come from the write response; otherwise the fields that were sent are matched. Not exempted by a declared 2xx network check (that validates the response, not persistence) nor by `reconcile` (runs only on unknown outcomes); exempted by `healthIgnore`, an expected non-2xx answer, or a declared `api` postcondition; off with `policy.readback: "off"`. Confirmations are listed in the result (`readback`).
  _Measured:_ positive control S16 (conventional REST silent drop, added after the feature, not held-out): Vedha 10/10 detected, pw-trust/pw-test/pw-strong 0/10 with the same typical declarations (an expert could hand-write the probe). Pre-registered widget silent drops: still 0/20 detected, because that fixture writes to `/api/event` and lists at `/api/events`, which the same-path convention does not pair; the planned target (>=70/80) was **not** met on that track and the fixture was not changed to fit. False-failure audit at n=5: 0 on S01-S16, held-out widgets, TodoMVC.
  _Limits:_ no coverage for GraphQL, separate read endpoints, filtered or per-user collections that omit the new item, eventually consistent stores slower than 1.2 s.
